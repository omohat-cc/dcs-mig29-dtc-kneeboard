## 1. TL;DR (the decision needed)

Replace the global hotkey (Item 5) with an **automatic** refresh: while you are
sitting on the ground in a MiG-29, the app watches the DTC temp file for changes
and regenerates the kneeboard on its own; once airborne it pauses; on landing it
resumes. The status window shows each transition.

Your instinct that "DCS fires takeoff and landing events" is **correct** - they
exist. But for a **client-side** hook on a **multiplayer** server those specific
events are the *less* reliable option. The research turned up a cleaner lever:
the hook you already ship can read your own aircraft's height directly, with no
new files and no dependency on event delivery. That is the recommended path.

Two things I need from you before writing the build prompt:

1. **Confirm the assumption** in section 3.4 (that you edit the DTC via the DTC
   manager panel, which DCS serialises to the temp file). This is load-bearing.
2. **Confirm the poll interval** (I recommend **5 seconds** on the ground;
   rationale in section 4.5). Made configurable either way.

## 2. Context: why move off the hotkey

- The hotkey (Item 5) needs a **system-wide** key grab (Win32 `RegisterHotKey`
  on a dedicated message-loop thread) so it fires while DCS/VR has focus. Your
  concern is real: DCS itself, SRS, TacView, VoiceAttack, vJoy/joystick software,
  Vaicom, etc. all register or listen for keys, and a global grab can collide
  (the combo silently fails to register, or it is swallowed before DCS sees it).
- The auto-refresh idea removes the key grab entirely. Nothing global is hooked;
  the app just watches a file. That is strictly less invasive than the hotkey and
  also less work for you in the cockpit (no key to remember or press).
- It reuses machinery you already built: the Regenerate path (Item 4,
  `generate_kneeboard(force=...)`), the change dedupe and the cheap mtime/size
  early-out (Item 1), and the existing 2-second watch loop.

## 3. Research findings (the events question, answered)

### 3.1 The events exist

In the GUI/hooks Lua state (the one your `hook_template.lua` runs in, via
`DCS.setUserCallbacks`), the `onGameEvent(eventName, ...)` callback does deliver
takeoff and landing:

| Event name  | Parameters                                   | Fires when                         |
|-------------|----------------------------------------------|------------------------------------|
| `takeoff`   | `(eventName, playerID, unitMissionID, airdrome)` | a unit gets airborne off a runway/ground |
| `landing`   | `(eventName, playerID, unitMissionID, airdrome)` | a unit touches down                |

(There are siblings too: `crash`, `eject`, `pilot_death`, `change_slot`, etc.)
So your memory is right: this is the same family of events Contention and HBCW
use. **Important distinction:** Contention/HBCW read them **server-side**, inside
the *mission scripting* environment (`world.event.S_EVENT_TAKEOFF` via
`world.addEventHandler`), which is authoritative. Your utility runs **client-side**
in the *hooks* environment. Same idea, different and weaker guarantees.

### 3.2 The catch: client-side delivery in multiplayer

The hook callbacks split into two kinds:

- **Local-truth callbacks** that the client always sees for itself, e.g.
  `onSimulationFrame` (every rendered frame) and `onPlayerChangeSlot` (your slot
  changes; in MP you also see *others'*, which is exactly the v1.1 bug you fixed).
- **Game/world events** (`onGameEvent` takeoff/landing) that are generated by the
  **simulation authority**. On a dedicated-server mission your client is not the
  authority, and ED's own changelogs/forum history show takeoff and landing
  events behaving **differently for host vs client** and periods of them **"not
  registering"** for clients. They are reliable on the server; on a client they
  are "usually, eventually, mostly" - not a foundation I would build a paused/
  resumed loop on.

Net: building the air/ground gate on `onGameEvent` would work in single-player
and probably most of the time in MP, then silently fail to resume polling after a
landing on some server, on some patch. Hard to debug, easy to distrust.

### 3.3 The better lever: read your own height from the hook directly

The hooks Lua state has the **Export API available in-process** (Hoggit's
gameGUI reference: "the export lua environment is available here ... functions are
prefaced with `Export.`"). So from inside the hook's `onSimulationFrame` you can
call:

```lua
local agl = Export.LoGetAltitudeAboveGroundLevel()   -- metres above terrain
-- and/or
local self = Export.LoGetSelfData()                  -- ownship table (pos, etc.)
```

Why this is the right tool here:

- It is **local ownship truth**. It reflects *your* aircraft, read on *your*
  client, every frame, identically in SP and MP. No event delivery, no host/client
  divergence.
- It needs **no change to `Export.lua`**. This matters - your spec deliberately
  avoids touching `Export.lua` (it is a shared file other tools cooperatively
  chain). We are not touching it. We call `Export.*` from the hook you already own.
- `LoGetSelfData()` specifically is documented as **not gated by the server's
  anti-cheat/export setting** (it is how SRS gets your position even on locked
  servers). `LoGetAltitudeAboveGroundLevel()` lives in the "Ownship" export group,
  which a server *can* disable - so the design treats a `nil` reading as "unknown,
  keep polling" (safe fallback, section 4.2), and can fall back to
  `LoGetSelfData()` altitude if needed.

This keeps the whole air/ground decision inside the single hook file, pcall-guarded
like everything else there.

### 3.4 The load-bearing assumption (please confirm)

The whole feature assumes that **when you change the DTC after slot-in, DCS writes
the new cartridge to the `~tr*.bin` temp file** - because that file is all the app
can read. What we know:

- **Confirmed (gotcha 9, from your live testing):** applying a config in the DCS
  **DTC manager panel** writes a fresh serialisation to the temp file (the file
  accumulates many copies; `bin_parser` already reads the newest). So edits made
  through the DTC manager **are** caught by polling.
- **Unverified (spec section 10, research item #3):** whether fiddling values
  directly via the 3D-cockpit devices (PVI-800 etc.) **outside** the DTC manager
  also rewrites that temp file. The Regenerate button (Item 4) already carries this
  same caveat.

**Assumption I am proceeding on:** "edit the DTC config in the cockpit" means you
re-open the **DTC manager** while slotted in and apply changes. If that is what you
do, polling works. If you mean hand-jamming the 3D pit instead, polling may see
nothing and we should confirm on a live test before relying on it. Either way the
feature never makes things worse than today; at worst a given edit path is simply
not detected, exactly as now.

## 4. Recommended design

### 4.1 Division of labour

Two components, clean seam, both additive (nothing existing is removed):

```
HOOK (in DCS, client-side)                      APP (external watcher)
--------------------------                      ----------------------
Detects MiG-29 (today)            -- trigger -->  Generate once on spawn (today)
Tracks on-ground / airborne   --- state file -->  Decide whether to watch the .bin
  via Export AGL + hysteresis                     While on ground: if .bin changed,
                                                    regenerate (force=False, so the
                                                    content dedupe still applies)
                                                  While airborne: pause the watch
                                                  Reflect phase in the status window
```

- The **hook** is the only place that can know your height, so it owns the
  air/ground decision and publishes it.
- The **app** is the only place that can read/parse the `.bin`, so it owns change
  detection and rendering.
- The existing **trigger** path (spawn -> generate now) is untouched and still
  does the first render. The new path only adds "while parked, catch later edits".

### 4.2 Ground/air detection in the hook (state machine)

A small, always-cheap addition to the existing `onSimulationFrame`, active only
while the local unit is a MiG-29:

- On a confirmed MiG-29 (the existing `poll()` success path), set `migActive=true`
  and initialise `phase="ground"` (ramp and runway starts are on the ground; an
  air start, which these servers rarely use, self-corrects within ~1s on the first
  AGL read).
- Every `STATE_POLL_FRAMES` (~60 frames ≈ 1s), read `agl =
  pcall(Export.LoGetAltitudeAboveGroundLevel)`:
  - `agl == nil` (in a menu, spectating, briefly between states, or ownship export
    disabled by the server): **leave phase unchanged.** Default stays "ground", so
    we keep polling - the safe direction.
  - **Hysteresis** (two thresholds so it cannot flap on bumps / the takeoff roll):
    - phase ground -> air when `agl > AGL_AIR_M` (e.g. 30 m) for `N` consecutive
      samples (e.g. 3).
    - phase air -> ground when `agl < AGL_GROUND_M` (e.g. 10 m) for `N` consecutive
      samples.
- On any phase change, write the state file (section 4.3). Also re-write it on a
  slow heartbeat (e.g. every 10s) so the app can tell DCS is alive.
- On slot change to a non-MiG-29 or empty slot, and on `onSimulationStop`, set
  `migActive=false` and write `phase="none"`.

All thresholds/frame-counts are named constants. Everything is pcall-wrapped; a
failure degrades to "ground" (keep polling), never crashes the sim loop.

Optional refinement (not required for v1): also gate on `LoGetVerticalVelocity` or
`LoGetIndicatedAirSpeed` for a crisper takeoff edge. I would ship AGL-only first;
it is simpler and enough for "am I parked or flying".

### 4.3 The state-file contract

New file, written by the hook, read by the app. Small JSON, same `Logs` folder and
same atomic write-then-rename pattern as the trigger:

```
<Saved Games>\DCS\Logs\dtc_kneeboard_state.json
{
  "phase": "ground" | "air" | "none",
  "aircraft": "MiG-29S",
  "agl_m": 2.4,                       // last reading, for the log/diagnostics
  "ts": "2026-06-24T09:15:03Z"        // UTC; lets the app detect a stale hook
}
```

App interpretation each loop:
- File missing or `ts` older than `STATE_STALE_SECONDS` (e.g. 30s) -> treat phase
  as **unknown**; behave exactly like today (trigger-driven only, no ground poll).
  This cleanly handles "DCS not running" and "old hook with no state file".
- `phase == "ground"` -> run the `.bin` change-check (below).
- `phase == "air"` or `"none"` -> skip the change-check; show the paused state.

Keeping it a separate file (not folded into the trigger) means the spawn path and
the phase path never stomp each other, and an older hook that does not write it
simply leaves the app in today's behaviour.

### 4.4 App watcher changes

In `trigger_watcher.py`, extend the existing loop (it already wakes every 2s):

1. Read `dtc_kneeboard_state.json` (cheap; tiny file). Derive `phase`.
2. Keep handling the trigger exactly as today (spawn -> `generate_kneeboard()`).
3. **New:** if `phase == "ground"`, every `GROUND_POLL_SECONDS` do a change-check:
   - Find the newest candidate `~tr*.bin` (the logic Item 1B already added) and
     read its `(path, mtime, size)`.
   - If unchanged since the last generation -> do nothing (no parse, no render).
   - If changed -> call `generate_kneeboard()` **with `force=False`** so the
     content fingerprint dedupe (Item 1A) still guards against a no-op rewrite.
     Net effect: a real DTC edit regenerates; anything else is silently ignored.
4. Surface phase transitions to the status log (section 4.6).

Note we deliberately use `force=False` here (unlike the manual Regenerate button,
which forces). On the ground we are polling speculatively, so we *want* the dedupe;
only a genuine content change should redraw.

This is all on the existing daemon thread, no new threads, no new dependencies.

### 4.5 Poll interval recommendation: 5 seconds (configurable)

The per-poll cost on the ground is tiny: list the temp dir, stat the newest
candidate, compare mtime/size. The expensive work (extract + parse + Pillow render)
only runs when the file actually changed, and even then the content dedupe can drop
it. So the interval is purely a responsiveness-vs-tidiness choice, not a performance
one.

| Interval | Feel                              | Verdict |
|----------|-----------------------------------|---------|
| 3s       | snappiest; marginally more dir scans, no real downside | fine, slight overkill |
| **5s**   | kneeboard catches up a few seconds after you apply a DTC; comfortably below the patience threshold while parked | **recommended default** |
| 10s      | noticeable wait staring at the pit | acceptable, a bit sluggish |
| 30s      | feels broken when you are waiting  | too slow |

Recommendation: **default 5s**, exposed in `config.json`
(`ground_poll_seconds`, with a sane floor like 2s and a clamp). 3s is a perfectly
reasonable alternative if you want it snappier; I would not go above 10s.

(Separate, unrelated point worth a live check: DCS only re-reads a kneeboard page
image at certain moments - page turn / kneeboard toggle / respawn. Even a 1s app
refresh cannot beat DCS's own redraw cadence, which is another reason not to chase
a very short interval.)

### 4.6 DTC Watch label (3 states) + status-window messages

A small always-visible label on the window showing the current watch state
(confirmed with Omar). It maps directly off the state file the hook publishes:

| Label     | Meaning                                  | Source (state-file phase)                |
|-----------|------------------------------------------|------------------------------------------|
| **Waiting** | Not slotted in a MiG-29 (or no live DCS) | `none`, or file missing / stale (>30s)   |
| **Ground**  | In a MiG-29, on the ground, watching the temp file | `ground`                       |
| **Paused**  | In a MiG-29, airborne (watch paused)     | `air`                                    |

The label updates live via an `on_phase_change` callback (same marshal-via-queue
pattern as the generation sound, so the watcher stays GUI-free and nothing touches
Tk off-thread). The scrolling status log still prints the transitions:

- On ground, watch starting: `MiG-29 on the ground - watching DTC for changes
  (every 5s).`
- Change caught: `DTC change detected on the ground - regenerating kneeboard.`
- Takeoff: `Airborne - DTC watch paused.`
- Landing: `Back on the ground - DTC watch resumed.`
- Hook went away / DCS closed: `No live DCS state - watching for the next spawn
  trigger only.`
- (Existing spawn/trigger/generated/error messages unchanged.)

## 5. Options considered

| Option | How it gets air/ground | MP client reliability | Invasiveness | Verdict |
|--------|------------------------|-----------------------|--------------|---------|
| **A. Export AGL polling in the hook** | `Export.LoGetAltitudeAboveGroundLevel` in `onSimulationFrame`, hysteresis | High (local ownship truth) | Low (one hook file; no Export.lua edit) | **Recommended** |
| B. `onGameEvent` takeoff/landing | event callbacks in the hook | Medium/low (host vs client divergence, historical "not registering") | Low | Rejected as the gate; nice-to-have fast-path at most |
| C. Global hotkey (original Item 5) | n/a (manual) | n/a | High (system-wide key grab, collision risk you flagged) | Superseded |
| D. App polls the .bin always (no gate) | n/a | n/a | Low | Works, but never pauses airborne; ignores your explicit ask and wastes some scans |

A is B's reliable cousin: same outcome ("am I flying?"), sourced from a signal the
client always has. If we ever want B as a low-latency hint on top of A, it can be
added later without redesign.

## 6. Edge cases

| Scenario | Behaviour |
|----------|-----------|
| Cold/hot ramp start | phase=ground immediately; watch active. |
| Runway start | phase=ground; first AGL read confirms; watch active until rotation. |
| Takeoff roll bumps / brief hops | hysteresis + N-consecutive-samples prevents flapping. |
| Air start (rare on these servers) | phase=ground for ~1s, then corrects to air on first AGL read; harmless. |
| Touch-and-go | dips toward ground then climbs; may or may not flip to ground briefly; either way safe (worst case one extra cheap change-check). |
| Server disables ownship export | AGL reads nil -> phase stays ground -> app keeps polling on the ground. You lose the airborne pause on that server only; cheap early-out keeps it harmless. |
| DCS not running / app started later | state file missing or stale -> app behaves exactly like today. |
| Old hook (no state file) after app update | app falls back to today's trigger-only behaviour; no crash. |
| Different aircraft / slot exit | phase=none; watch off. |
| Mid-air DTC change (if even possible) | not caught while airborne by design; the manual Regenerate button (Item 4) is still there as the escape hatch. |

## 7. What actually changes in code

Hook (`App/hook_template.lua`), bump to **v1.2**:
- Add the AGL state machine in `onSimulationFrame` (active while `migActive`).
- Add `writeState(phase, agl)` (atomic, pcall-guarded), plus the heartbeat.
- Set `migActive`/`phase` on the MiG-29 detect, slot-exit and `onSimulationStop`.
- Keep every existing safety constraint (pcall all DCS/Export calls, no
  `getMissionLoaded`, no `Export.lua` edits). The version bump makes `hook_manager`
  auto-update the installed hook.

App:
- `trigger_watcher.py`: read the state file; add the ground change-check path
  (reusing Item 1B's newest-`.bin` + mtime/size cache and Item 1A's dedupe);
  emit the phase log lines.
- `config.py`: add `ground_poll_seconds` (default 5) and maybe
  `state_stale_seconds` (default 30); `to_json_dict`/`from_dict`; bump
  `CONFIG_VERSION`.
- `main.py`: nothing structural - the new log lines flow through the existing
  `QueueLogHandler` bridge. (Optional: a small "DTC watch: ground/paused" label.)
- Tests: drive `poll_once()` with a synthetic state file = ground + a changed vs
  unchanged `.bin` fixture; assert it regenerates only on change, and that
  air/none/stale skip the change-check. All Mac-testable headless; the hook AGL
  behaviour needs a live Windows/DCS check.

Constraints unchanged: UK English, no em dashes, type hints, docstrings, file I/O
in try/except, no new runtime deps, watcher stays importable headless and never
crashes.
